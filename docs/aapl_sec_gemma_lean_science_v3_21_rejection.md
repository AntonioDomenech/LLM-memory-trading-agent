# AAPL SEC/Gemma lean science v3.21 pre-implementation rejection

## Decision

V3.21 is permanently rejected before an `I321` implementation commit,
official one-shot preflight reservation, development attempt, Yahoo request,
Ollama request, Gemma generation, market-value read, prediction, action,
return, performance calculation, confirmation or live-style data open, paid
API, broker action, or real-money action.

The exact twelve-file working candidate correctly carries the 4,800-second
whole-preflight deadline, deterministic `_strptime` preload, direct
publication-recovery authority, and candidate-less zero-effect recovery from
P321. It nevertheless contradicts the frozen runtime contract: the real
isolated source-chain node observed 3,243 protected callables, while P321
requires exactly 3,242. Repository, dependency, loaded-code, and process-object
identity remained equal before and after that chain, so this is one exact
preregistration mismatch rather than general runtime drift.

Knowingly creating `I321` after this result would turn a discovered mismatch
into a mislabeled implementation. The candidate therefore remains uncommitted,
the official reservation remains unused, and V3.21 has no strategy result.

## Correction to the V3.20 diagnosis

The V3.20 rejection attributed its observed 3,243-versus-3,242 mismatch
exactly to the intermediate runner callable
`build_production_development_dependencies.<locals>.authenticate_recovery`.
That attribution was incomplete and wrong as an explanation of the protected
count difference.

The V3.21 runner has no such wrapper. Its production dependency binds the
dedicated recovery authority directly to
`load_publication_recovery_authority`, exactly as P321 requires. Nevertheless,
the wrapper-free manifest still contains 3,243 protected callables. The exact
graph differential above identifies the historical-pins helper as the sole
added row. The preserved V3.20 rejection remains an honest record of what was
believed then; this V3.21 rejection is the evidence-backed correction and does
not rewrite that historical file.

The `_strptime` correction is also behaving as intended. It changes the
dependency module-file inventory from the old 365 to the stable 366; it does
not explain the one added repository callable.
